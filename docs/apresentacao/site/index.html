QuebraCódigo

Plataforma educacional — o foco desta fala: como o projeto sobe e fica no ar.

Docker · Supabase · VPS

Contexto

O projeto em 20 segundos

  • App web: cursos, jogos, login e progresso
  • Spring Boot (Java 21) + HTML/CSS/JS · porta 8150
  • Antes: cada um rodava na máquina · Agora: container + nuvem + servidor

Pilares

Três implementações

Docker

Empacota e sobe a app igual em qualquer máquina.

Supabase

PostgreSQL na nuvem — banco compartilhado do time.

VPS

Servidor 24h com a imagem Docker + .env.

Docker

O que implementamos

  • app/Dockerfile — build multi-stage (Maven → JAR → JRE)
  • docker-compose.yml — sobe a app com credenciais do .env
  • network_mode: host — evita timeout SSL com o pooler Supabase
  • docker-compose.local-db.yml — override opcional com Postgres local

Docker

Por que importa

  • Mesmo ambiente — sem “na minha máquina funciona”
  • Um comando — docker compose up --build
  • Base da VPS — o que roda local é o que sobe no servidor
  • Local opcional — Postgres no Docker quando precisar offline / não sujar o banco da nuvem

Supabase

O que implementamos

  • PostgreSQL gerenciado na nuvem (banco oficial do projeto)
  • Schema app — evita permission denied for schema public
  • Session Pooler (IPv4) — URL direta db.* falha em redes só IPv4
  • Flyway + Hibernate apontam para currentSchema=app
  • Credenciais via .env (modelo em .env.example)

Supabase

Por que importa

  • Banco único — time e VPS falam com a mesma base
  • Sem instalar Postgres em cada PC para o fluxo padrão
  • Backup e acesso pelo dashboard (SQL Editor, etc.)
  • Produção de verdade — a app na VPS não depende do notebook de ninguém

VPS

O que implementamos

  • docker-compose.vps.yml — usa imagem pronta quebracodigo-app:latest
  • Sem Maven na VPS — só sobe o container (mais leve e rápido)
  • App na VPS · banco no Supabase · secrets no .env
  • Limite de memória (-Xmx384m) + pool Hikari menor + restart: unless-stopped

VPS

Por que importa

  • URL pública — banca e time acessam sem “abre aí no teu PC”
  • Disponibilidade — servidor ligado 24h, com reinício automático
  • Controle — nós definimos porta, RAM e como atualizar o deploy
  • Entrega de TCC — demonstra ops real: container + nuvem + hospedagem

Juntos

Como as peças se ligam

  1. Docker empacota a app Spring
  2. Supabase guarda os dados (schema app)
  3. VPS roda o container e expõe a porta 8150

Usuário → VPS (Docker) → Supabase (PostgreSQL)

Na prática

Como o time sobe

  1. Padrão — .env + docker compose up --build → Supabase
  2. Opcional — + docker-compose.local-db.yml → Postgres no PC
  3. Produção — imagem + docker-compose.vps.yml na VPS

Local Postgres = plano B · Supabase = banco oficial

Fechamento

Em uma frase

Docker padroniza a execução; Supabase centraliza o banco; a VPS coloca o QuebraCódigo no ar.

  • Docker — build, compose, mesmo ambiente
  • Supabase — schema app + Session Pooler
  • VPS — imagem pronta, sempre disponível
